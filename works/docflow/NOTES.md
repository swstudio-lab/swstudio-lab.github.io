## 글자 읽기 (OCR) — 2026-10-08 구현

### 원칙
- **브라우저 안에서만 처리한다.** 서버·API 키 없이 Tesseract.js(WebAssembly)로 기기 안에서 읽는다. 문서가 밖으로 나가지 않는다.
- **엔진·언어 데이터는 CDN이 아니라 `assets/vendor/tesseract/`에서** 불러온다(출처·라이선스는 그 폴더의 README.md).
  "글자 읽기"를 실행할 때만 불러오므로, OCR을 쓰지 않으면 기존 기능·로딩 속도는 그대로다.
  - 저장소 용량 12.5MB. 사용자가 처음 OCR 할 때 받는 양 약 8.6MB(코어 3.9MB + 한국어 1.6MB + 영어 3.0MB + 스크립트).
    다음부터는 브라우저 캐시·IndexedDB에서 바로 불러온다.
  - 코어는 LSTM 전용 두 가지만 넣음: SIMD 되는 브라우저는 simd-lstm, 안 되면 lstm(DocFlow가 직접 골라 지정).
  - 언어 데이터는 best_int(정수형 LSTM) — tesseract.js 기본값, 정확도·크기 균형.
- "글자 읽기 (OCR)"는 체크 항목으로, 처리할 때 맨 마지막에 자동 실행(OCR 최적화 프리셋에 포함).
  체크돼 있으면 이미지 처리하는 동안 엔진을 미리 받아 둔다.

### 엔진 불러오기·실패 처리 (2026-10-12, Live Server에서 "글자 읽기를 실행하지 못했어요" 신고 후)
- 언어 데이터는 엔진 자체 캐시(IndexedDB)를 쓰지 않음(`cacheMethod: 'none'`) — 엔진 캐시가 깨져 있으면 한국어 데이터를
  못 열고도 실패를 알리지 않은 채 영어만으로 읽었음. 파일은 이 사이트에서 받으므로 브라우저 HTTP 캐시가 대신 재사용함.
- 실패 단계 기록(`ocrStage`: 엔진 파일 → 엔진 시작 → 언어 데이터 → 준비 → 인식)과 단계별 안내(`ocrFailMessage`).
  "인터넷 연결" 안내는 실제로 오프라인일 때만. 자세한 오류는 Console에 `[DocFlow OCR]`로 남김.
- 실패하면 작업자를 버리고 한 번 더 시도(작업자를 blob 주소 대신 파일 주소로).
- 멈춤 방지: 미리 받기가 실패한 `<script>`가 남아 다음 시도가 영원히 기다리던 문제 수정, 엔진이 언어 파일 404를
  오류로만 알리고 작업자 생성을 끝내지 않던 것을 오류 즉시 실패로, 90초 동안 진행이 없으면 실패로 봄(감시 장치).
- 테스트: `run_tests.py serve` — 진짜 정적 서버(Live Server와 같은 방식)를 띄워 사용자처럼 업로드→OCR 최적화→처리,
  엔진·언어 파일을 못 받는 경우까지.

### 직인(빨간색)은 OCR에 넣는 이미지에서만 뺀다
- **사용자에게 보이는 결과물(다운로드되는 이미지·PDF)에서는 직인을 지우지 않는다.**
  결과물이 증빙서류로 쓰이기 때문에, 직인은 문서의 진위를 보여주는 부분으로서 그대로 남아야 한다.
  - 스캔 효과 컬러 모드: 직인 색 그대로 유지
  - 스캔 효과 흑백 모드: 직인을 연한 회색으로 남김 (아래 검은 글자는 읽힘)
  - 흑백 복사본처럼 원래부터 회색인 직인도 그대로 둔다 (사진 05 사례)
- **OCR 엔진에 넘기는 이미지는 내부적으로 따로 만든다** — `prepareOcrImage()`
  - 컬러 결과: `findStampRegions()`로 찾은 직인 안의 붉은 픽셀만 흰색으로(빨간 숫자·강조 글씨는 그대로)
  - 흑백 결과: 직인이 이미 연회색(약 205)이라, OCR 이미지에서만 아주 연한 회색(200 이상)을 흰색으로
- OCR 입력은 회색조. 완전 이진화는 하지 않는다 — Tesseract가 자체 이진화를 하고, 미리 이진화하면 획이 뭉개진다.

### 어두운 바탕 + 밝은 글씨 (사진 01의 파란 띠 안 흰 글씨)
- `findInvertedTextRegions()`로 찾음: 흰 글씨를 지운 바탕이 어두운 덩어리 중 띠·칸 모양이고(열마다 채운 비율 80%↑,
  두께가 긴 변의 1.1%↑), 대부분 어둡고(75%↑) 밝은 획이 1~35%인 것. 띠의 위·아래 경계는 직선으로 맞춰 그 사이만 씀.
  - 굵은 제목·굵은 숫자는 "어두운 덩어리"로 잡히지만 어두운 비율 50~60%·밝은 비율 40~50%라서 빠짐
    (이 조건이 없을 때 굵은 글자 획 사이가 뒤집혀 흰 얼룩이 생겼었음).
- **OCR 이미지**: 그 영역을 뒤집어 흰 바탕에 검은 글씨로.
- **보이는 흑백 결과**: 띠는 어둡게(30) 두고 글자만 거의 흰색이 되도록 대비만 늘림(`enhanceInvertedText()`).

### 언어: 한국어+영어로 읽고, 한글 사이에 낀 짧은 영문만 한국어로 다시 읽기 (2026-10-08)
한국어+영어로 읽으면 흐린 한글 단어가 엉뚱한 영어 대문자로 바뀜("계획을"→"AUR", "금액을"→"SHS", "시연용"→"AEE").
한국어만으로는 이런 일이 없지만 영문을 하나도 못 읽음. 실제 문서에는 사업명(RISE·LINC), 기관 영문명, 이메일·웹 주소가
섞여 있고, 이메일은 정보 가리기에서 찾아야 해서 반드시 읽혀야 함. 네 방식을 같은 조건(OCR 이미지 크기 조정 전)에서 비교함
(시연 문서 4장 + 한영 혼합 문서 2장 + 사진 05):

| 방식 | 시연 문서 정확도(깨끗/사진 평균) | 한영 혼합 정확도(깨끗/사진) | 엉뚱한 영어(1쪽 깨끗/사진) | 영문·이메일(혼합 깨끗/사진) | 속도 |
|---|---|---|---|---|---|
| ① 한국어만 | 90.0% | 45.8% / 41.4% | 0 / 0 | 0/13 / 0/13 | 가장 빠름(약 35%↓) |
| ② 한국어+영어 (이전) | 89.7% | 95.1% / 90.4% | 5 / 8 | 9/13 / 5/13 | 기준 |
| ③ 한국어로 읽고 영문처럼 보이는 단어만 영어로 다시 | 90.7% | 84.0% / 93.1% | 1 / 1 | 5/13 / 6/13 | ①과 비슷 |
| **④ 한국어+영어로 읽고, 한글 사이 짧은 영문만 한국어로 다시 ← 채택** | **90.3%** | **95.6% / 91.4%** | **3 / 6** | **9/13 / 5/13** | ②와 거의 같음(+0.1초) |
- ③은 한국어 모델이 영문 단어를 한글 조각으로 읽어 버리면 "영문 후보"에서 빠져서 혼합 문서에 약함.
- ④의 다시 읽을 후보: 한글 단어 바로 옆의 **영문 글자만 2~4자** 덩어리. 이메일·주소·숫자 섞인 것·5자 이상은 진짜 영문일
  가능성이 커서 손대지 않음(처음엔 모든 영문 단어를 후보로 했더니 사진 속 웹 주소·"LINC"가 한글 엉터리로 바뀜).
  한국어 재판독 결과가 **한글만이고 확신도가 15 이상 높을 때만** 바꿈.
- 다시 읽기는 같은 작업자에서 영문 글자를 금지(`tessedit_char_blacklist`)하고 후보 단어를 한 장에 모아 한 번에 읽음 —
  한국어 전용 작업자를 하나 더 띄운 것과 결과가 완전히 같고, 휴대폰 메모리가 늘지 않음.
- 다시 읽어도 영문으로 남은 이런 덩어리는 확신도 85 미만이면 `suspect`로 표시해 "확신 낮은 단어"에 넣고, 텍스트 창 안내에
  예시로 보여줌(예: "확신 낮은 단어 2개 (예: (₩3,250,000), SUS)").

### 읽은 글자 후처리 — `cleanOcrLine()` (쪽 글자·줄·단어에 똑같이)
- 숫자 앞의 "\"는 "₩"로 바꿈(Tesseract가 원화 기호를 역슬래시로 읽음).
- **혼자 떨어진 기호 지우기**: 앞뒤가 공백인 "、_", "。", "__", "|", "ㅣ"(표 테두리) 같은 덩어리만 지움 — 표의 줄 앞에 붙어 나왔음.
  단어에 붙은 마침표·쉼표는 그대로. "-"(표의 "없음"), "~"(시간 범위), "·", ":"는 뜻이 있어서 남김.
- **이메일·웹 주소의 빠진 점 되살리기**: 엔진이 원본에서도 점을 놓침("gdhong@mail.ganauniv.ackr", "help@docflowkr",
  "wwwganaunivackr", 점이 공백이 된 "ganaunivac kr"). @ 뒤·"://" 뒤·"www"부터의 주소 부분에서만 고침:
  주소 안 공백 → 점(뒤 조각들이 kr·com·net·org로 끝날 때만 이음 — 주소 뒤 일반 단어는 안 붙임), "www" 뒤·끝의
  kr·com·net·org 앞·한국 2단계 도메인(ac·co·go·or·re·ne 등) 앞에 점, "httpi//" → "http://", "httpsrise…" → "https://rise…".
  @ 앞(아이디)은 점인지 밑줄인지 알 수 없어서 건드리지 않음. 고친 주소는 "확신 낮은 단어"(`suspect`)로 표시하고
  결과의 `addrFixes: [{from, to}]`로 돌려줌(정보 가리기에서 이메일 후보로 씀).
- 혼합 문서 사진의 이메일·웹 주소 4개: 후처리 전 정확히 읽힌 것 0개 → 후처리 후 3개(help@docflow.kr,
  https://rise.ganauniv.ac.kr/notice, www.ganauniv.ac.kr/rise/report). 나머지 kim.gana@ganauniv.ac.kr은 도메인은
  살아났지만 아이디의 점이 빠지고 g→q로 읽힘.

### 이미지 처리 쪽 함께 고친 것 (OCR 정확도에 영향)
- 노이즈 제거: 글자 바로 옆(몇 px 안)의 작은 점은 지우지 않음 — 이메일·웹 주소의 마침표가 잡티로 지워졌었음.
- 여백 정리: 글자가 드문 줄(한 줄만 길게 뻗은 오른쪽 끝 등)까지 내용인데 여백으로 잘라 글자가 잘렸었음 → 확실한 내용
  경계에서 바깥쪽으로, 빈 줄이 짧은 변의 2.5% 넘게 이어지기 전까지 넓힘.
- 스캔 효과(흑백): 연하게 칠해진 칸을 칸 단위로 고르게 — 칸 하나는 전체가 고른 연회색이거나 전체가 흰색.
  넓게 이어진 연한 칸은 가장자리만 회색, 가운데는 흰색으로 남아 둥근 흰 얼룩이 생겼었음(지출결의서 항목 칸).
  회색이 조금 남은 칸은 바로 위아래(좌우)의 같은 크기 회색 칸과 줄이 맞으면 같은 회색으로 맞춤. 흑백 직인은 건드리지 않음.

  지금 크기에서 글자(획 덩어리) 높이가 이미 15~22px로 Tesseract가 잘 읽는 범위.
- 원본 해상도가 OCR까지 전달되는지: 원근 보정 결과 최대 크기를 2400 → 3500px로 올리면 사진 01 원본 결과가 2297×1676 →
  3188×2233이 되지만, 신뢰도는 72~77%(설정별)로 지금(75%)과 비슷하고 이미지 처리 시간은 10.0초 → 16.6초로 늘어남.

- 결론: 고정 크기(2000)를 그대로 둠. 글자 높이 기준은 평균이 같아서 바꿀 이유가 없음.

### 다른 기능에서 쓰는 법 (표를 엑셀로 · 정보 가리기)
- `ocrRecognize(canvas, { rect, mode, onProgress, prepare })` — 이미지 전체든 잘라낸 칸 하나(`rect: {x,y,w,h}`)든 같은 함수.
  - 결과 `{ text, meanConf, lowConfWords, lowConfList, lines:[{text,conf,bbox}], words:[{text,conf,bbox,suspect?}], ms, ocrCanvas }`
  - `bbox: {x0,y0,x1,y1}`는 모두 **넘겨준 canvas 기준 좌표** → 정보 가리기는 `words[].bbox`로 가림 상자를 그리면 됨.
  - `conf`(0~100)가 `OCR_LOW_CONF`(60) 미만이거나 `suspect`면 "확신 낮음" → 엑셀에서 확신 없는 칸 표시에 씀.
  - 칸은 여백을 붙이고 글자 높이가 작으면 최대 4배까지 키워서 읽음. 인식은 한 번에 하나씩 순서대로(작업자 하나 재사용).
- 엑셀: `findTableLines()`로 칸을 나누고 칸마다 `ocrRecognize(canvas, { rect, mode:'block' })`.
- 정보 가리기 — 이메일 찾기 주의: 사진에서는 이메일의 점이 빠지거나("ganauniv.ac kr") @ 앞뒤가 붙어서 읽히기도 함.
  정규식은 점이 빠진 형태(`아이디@도메인 kr`)도 후보로 잡고, 확신 낮은 이메일은 사용자 확인을 받는 게 안전.

## 캔버스 설정 — 처리용 캔버스는 `willReadFrequently` (2026-10-12)
- 픽셀을 자주 읽는 처리용 캔버스는 `getContext('2d', CTX_READ)`(= `{ willReadFrequently: true }`)로 만듦 —
  GPU 대신 CPU 메모리에 두어 읽을 때마다 GPU에서 복사하는 비용이 없음. 캔버스를 처음 만들 때 정해지므로 만드는 곳부터 넣음.
  화면에 그리기만 하는 캔버스(결과 미리보기·모서리 화면·돋보기·도장 미리보기·서명 카드·직접 그리기·PDF 렌더링)는 그대로.
- 측정(사진 01 카톡·원본, 03, 05 / OCR 최적화·문서 보관·도장 추출):
  - Console의 willReadFrequently 경고 60번 → 0번
  - 결과 픽셀: 적용 전후 같음(GPU 끈 브라우저 기준)
  - **GPU를 켠 브라우저에서는 적용 전 결과가 달랐음** — 사진 01이 테스트 1703×1104인데 GPU 켜면 1783×1292.
    GPU 캔버스의 그리기·읽기가 미세하게 달라 모서리 검출 같은 판단이 바뀜. 적용 후에는 GPU를 켜든 끄든 픽셀까지 같음 →
    실제 사용자 컴퓨터와 테스트 결과가 같아짐
  - 속도: GPU 켠 브라우저에서 5~9% 빨라짐(사진 01 원본 11.3초 → 10.2초), GPU 끈 브라우저에서는 차이 없음(±5%)

- 자동 검출은 "제안"일 뿐 — 놓치거나 잘못 잡을 수 있다고 화면에 적음.

### 1단계 — OCR 결과 확장 + 검출·가리기 함수 (쪽 하나 단위)
- `ocrRecognize()` 결과에 추가: 단어 `line`(lines 번호)·`chars:[{t, bbox}]`(엔진의 글자 단위 위치), 줄 `para`(문단 첫 줄).
  인식 결과 자체는 그대로(OCR 정확도 테스트 숫자 변화 없음).
- 가린 영역 `redaction = { mode:'full'|'partial', brush, items }` — 쪽 결과에 붙여 기억. item:
  `{ id, kind, auto, words:[단어 번호], partial:[[단어, 글자]], text }`, 형광펜은 `kind:'stroke', points, width`.
  좌표는 그 쪽 결과 이미지 기준.
- `detectSensitive(ocr)`: 줄마다 단어 글자를 이어 붙이고(문자열 위치 → 단어·글자 번호), 숫자 자리 오인식(O→0, l·I·|→1)을
  맞춰서 찾음. 같은 글자를 두 종류로 잡지 않음(먼저 잡은 것 우선: 주민 → 전화 → 계좌 → 이메일).
  - 주민·외국인: 생년월일 날짜 확인 + 성별 1~4(주민)·5~8(외국인) + 6자리. 일부만 = 성별 자리 **뒤** 6자리.
  - 전화: 01X / 0X(X) + 가운데 3~4 + 4자리, 구분자 `-` `.` `)` 공백. 일부만 = 가운데 묶음.
  - 계좌: 하이픈 숫자 묶음 10~16자리, 날짜·사업자등록번호(3-2-5) 제외, 같은 줄·윗줄에 계좌·통장·예금주·은행·입금이
    있거나 12자리 이상. 하이픈 없는 11~14자리는 계좌 단서가 있을 때만. 일부만 = 가운데 묶음.
  - 이메일: @가 있는 단어(점을 되살린 주소 포함). 바로 앞에 붙은 영문 조각(점이 공백이 된 아이디)도 함께.
- `redactionShapes` → 상자·획, `applyRedaction(canvas, ocr, red)` → 새 캔버스, `redactOcrText(ocr, red)` → 가린 글자를 ■로
  (일부만이면 그 글자만, 형광펜이 지나간 단어는 전부), `redactItemPreview` → 목록용(가린 글자를 ·로).
- 고친 것: 성별 자리를 `lastIndexOf(성별 숫자)`로 찾아 `920720-1357913`이 끝자리 하나만 가려졌음 → 끝에서 7번째로.
  "지급"·"수령"을 계좌 단서로 썼더니 제목 "강사료 **지급** 명세서" 아래 사업자등록번호가 계좌로 잡혔음 → 단서에서 뺌.

### 2단계 — 프리셋·처리 항목
- 프리셋 "📋 보고서 삽입"을 지우고 **"🕶️ 정보 가리기"**: 원근 보정·스캔 효과(컬러)·노이즈 제거·글자 읽기·정보 가리기, 저장 PDF.
- "문서 정리"에 "정보 가리기 (검토 후 저장)". 켜면 글자 읽기가 **체크된 채 흐리게 고정**("정보 가리기에 필요", `REQUIRED_BY`).
- 처리 순서 맨 끝 `redact` — 이미지는 바꾸지 않고 `processPage()` 결과에 `redaction`(자동 검출)만 붙임.
  글자 읽기가 실패해도 빈 목록으로 열려 형광펜으로는 가릴 수 있음. 가리기 방식·굵기는 `redactSettings` → `snapshotPageSettings().redact`.

### 3단계 — 검토 화면 (결과 아래 `#redactPanel`)
- 도구 줄: 👆 단어 고르기 / 🖍 형광펜(굵기 8~64px — **화면 기준**이라 확대해서 그으면 가늘게 칠해짐, "단어 대신 그은 자리 칠하기"),
  ↶ 되돌리기(Ctrl+Z도), 모두 해제, 🔍 −/+ (50~500%), 가리기 방식 ■ 전체 / □ 일부만.
- 문서 화면: 읽은 단어마다 옅은 파란 테두리, 가릴 곳은 반투명 검정, 자동 검출 = 노란 테두리, 직접 고른 것 = 빨간 테두리.
  목록: 종류·글자(일부만이면 가린 글자를 ·로)·"자동"(점 되살림이면 "자동, 점 되살림")·✕, 줄을 누르면 그 자리로 스크롤.
  형광펜으로 칠한 자리는 "🖍 형광펜으로 칠한 자리 N곳" 한 줄로 묶음.
- 휴대폰: 단어 모드는 `touch-action: manipulation`(한 손가락 = 평소 스크롤, 누르기 = click으로 선택). 형광펜 모드만
  `touch-action: none` — 한 손가락 = 칠하기(손가락 위 2배 돋보기), 두 손가락 = 스크롤·확대(두 번째 손가락이 닿으면
  긋던 획은 버림), 도구 줄이 화면 위에 붙음(sticky).
- **처음 확대**: 단어 높이 중앙값이 화면에서 14px쯤 되게(최대 300%) — 휴대폰 폭 100%에서는 글자가 7px쯤이라 누르기 어려웠음.
- **엔진이 한글 단어를 글자 하나씩 나누는 문제**: 가상 통장 사본에서 "홍길동"이 단어 `홍|길|동`, "계좌"가 `계|좌`로 나옴
  (줄 글자에는 붙어 있음). 그대로면 이름을 눌러도 한 글자만 골라짐 → `redactWordGroups()`: 줄 글자에서 공백 없이 이어진
  조각을 한 묶음으로, 누르면(형광펜에 걸려도) 묶음 전체를 고름. 붙어 있는 괄호까지 묶임("홍길동(가상)").
- 읽은 글자 창: 고를 때마다 `redactOcrText()`로 다시 채움 → 가린 글자는 ■, 복사도 가린 상태.
- 가리는 중에는 일반 "⬇ 다운로드"를 숨김(가리지 않은 결과를 실수로 받지 않게). 정보 가리기를 끄고 다시 처리하면 돌아옴.

### 4단계 — 저장 확인
- "가린 결과 확인하고 저장" → 확인 화면: 불투명 칠한 그림을 크게, 가린 곳 수, 저장 형식(PDF 증빙 제출용·PNG·JPG·WEBP —
  위 "저장 형식"과 같은 값), 형식별 안내(PDF는 그림 한 장·글자 층·문서 정보 없음 / 그림은 촬영 정보 안 붙음).
  [돌아가서 고치기] / [저장]. 파일 이름 `DocFlow_가림.pdf|png|jpg|webp`. 인앱 브라우저의 PDF는 기존처럼 안내 + 이미지로 받기.
- 저장 함수 정리: `saveBlobFile(blob, 이름)`을 따로 둠(`saveCanvasFile`이 이것을 씀).

### 7단계 — 가림 상자 모양: 네모 하나, 칸 밖으로 안 넘침 (사진 05 첫 번째 이름 상자가 울퉁불퉁하다는 신고 후)
- 원인: OCR 위치가 어긋난 게 아니라 **글자마다 따로 칠한 상자가 겹친 것**. 엔진이 이름을 글자 3개 단어로 나눴고, 가운데 글자
  상자만 높이 55px(나머지 26~27px)로 위아래로 늘어나 있었음. 두 번째 이름은 한 단어(상자 하나)라 괜찮았음.
- `redactionShapes()`:
  - 항목 하나는 **줄마다 네모 하나**(단어 상자들을 합침). 위아래는 정상 높이 상자들로 정함 — 높이가 중앙값의 1.5배를 넘는
    상자는 높이 계산에서 뺌. 이메일은 이 규칙으로 사이 점·@까지 덮임(따로 하던 처리를 합침). 일부만 가리기는 단어마다.
  - **칸 경계에서 자름** `clipToCell()`: 상자(여백 3px 포함)가 글자 가운데 기준 위·아래·왼·오른쪽 표 선을 넘으면 선 안쪽에서
    자름. 표 선이 글자 자체를 가로지르면(밑줄·취소선 등) 자르지 않음 — 글자가 드러나면 안 되므로.
- 표 선은 처리 중에 찾은 것을 씀(`pageTableLines`: 표 선 제거 단계나 OCR용 이미지에서 찾은 것, 같은 좌표). 원근 보정·여백 정리처럼
  모양·크기가 바뀌는 단계 뒤에는 버리고, 없으면 정보 가리기 단계에서 결과 이미지로 다시 찾음 → `redaction.lines`.
  - OCR 최적화 + 정보 가리기(표 선을 지운 뒤 여백 정리): 지우기 전에 찾은 선을 기억해 두고, 여백 정리가 잘라 낸 위치
    (`autoTrimMargins` 결과의 `trimOffset`)만큼 옮겨서 씀 — 사진 05에서 옮긴 선이 지워진 테두리 자리와 정확히 겹침을 눈으로 확인.

## 표를 엑셀로 (예정)

### 칸 나누기는 `findTableLines()`의 선 위치를 쓴다
- 표 선 찾기는 `findTableLines(canvas)`, 지우기는 `removeTableLines(canvas)`로 나뉘어 있다. 찾기만 하면 이미지는 바뀌지 않는다.
- 결과의 `segments.h`(가로 선, 위→아래 정렬), `segments.v`(세로 선, 왼→오 정렬)에 선분마다 `{x1,y1,x2,y2,thick,length}`가 있다.
  기울어진 사진이어도 선분 양 끝 좌표가 실제 기울기대로 나온다. 픽셀 단위 마스크는 `mask`(1=가로, 2=세로, 3=교차점).
- **같은 선이 여러 조각으로 나올 수 있다** — 흐리거나 중간이 끊긴 선, 칸이 합쳐진 머리글의 짧은 선.
  (사진 01 원근 보정본: 실제 가로 경계 약 25개 → 선분 39개, 세로 경계 11개 → 11개)
  칸을 나누기 전에 기울기·위치가 거의 같은(일직선인) 조각을 하나로 합치는 단계가 필요하다.
- 셀 병합(머리글의 합쳐진 칸)은 "두 경계선 사이에 선분이 없는 구간"으로 판단할 수 있다.
- 칸 OCR은 위 "다른 기능에서 쓰는 법" 참고.

## 여러 쪽 처리 계획 (예정 — 구조만 잡아 둠)

PDF 전체 쪽, 사진 여러 장 → 쪽마다 처리 → 한 PDF로 묶기.

### 이미 준비된 구조
- **`processPage(image, pageSettings, { page, onStatus })`** — 처리 흐름 전체(원근 보정 → 스캔 효과 → 표 선 제거 → … → 글자 읽기)를
  이미지 한 장에 대해 실행하고 `{ page, canvas, warnings, ocr }`를 돌려줌. 쪽마다 이 함수를 반복해서 부르면 된다.
- **쪽 설정 `pageSettings`** = `snapshotPageSettings()`의 결과: 체크 항목, 스캔 색상, 빈 칸 처리, 모서리 조정(`corner`: 자동/수동
  네 모서리/전체 사용, 회전), 서명 선택 영역. 복사본이라 쪽마다 따로 기억해 두면 된다.
  - 처리 함수들은 아직 화면 전역 상태를 읽으므로 `withPageSettings()`가 처리하는 동안만 그 쪽 설정으로 바꿔 두고 되돌린다.
    여러 쪽을 동시에(병렬로) 처리하면 안 됨 — 한 쪽씩 차례로.
- **OCR 결과는 쪽 단위** `{ page, text, words, lines, meanConf, … }`. `formatOcrPages(pages)`가 여러 쪽이면
  "── 1쪽 ──"으로 구분해 이어 붙임(텍스트 창용). `lastOcrPages`에 쪽마다 쌓으면 된다.
- PDF는 지금 첫 쪽만 처리하고, 여러 쪽이면 "📄 PDF는 첫 쪽만 처리돼요 (전체 N쪽 중 1쪽)"을 띄운다.

### 그때 같이 해야 할 것
- **OCR 쪽 구분**: 텍스트 창에 "── N쪽 ──" 구분, 쪽별 평균 신뢰도·확신 낮은 단어 수. 복사는 전체/현재 쪽.
- **정보 가리기 쪽별 검토**: 쪽마다 가릴 단어 후보를 보여주고 확인받기(쪽 넘김 UI). 가린 위치는 쪽 번호와 함께 저장.
- **표를 엑셀로 쪽별 처리**: 쪽마다 표를 찾아 시트 하나씩(또는 이어 붙이기 선택). 쪽 사이에 이어지는 표(머리글 반복) 처리.
- **휴대폰 메모리 관리**: 한 쪽씩 처리하고, 끝난 쪽은 작은 미리보기 + 압축(JPEG/PNG Blob)으로만 들고 있고 원본 크기 캔버스는 버림.
  PDF 쪽도 필요할 때 한 쪽씩 렌더링. OCR 작업자는 하나를 재사용.
- **최대 쪽 수 제한**: 예) 한 번에 20쪽(휴대폰은 더 적게). 넘으면 앞쪽만 처리하고 안내.
- **쪽마다 설정**: 모서리 수동 조정·회전은 쪽마다 다르므로 쪽 목록에서 쪽을 골라 조정하는 화면이 필요.
- **진행 표시**: "(3/12쪽) 표 선 지우는 중…"처럼 쪽 번호까지. 중간에 멈추기 버튼.
- **결과 묶기**: 처리한 쪽들을 jsPDF로 한 PDF로(쪽 크기는 각 결과 크기대로).
